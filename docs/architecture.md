# Архитектура проекта «Ёлкин двор»

## 1. Статус и назначение

Документ описывает **целевую архитектуру MVP**, а не утверждает, что перечисленные модели и механизмы уже реализованы. На момент подготовки документа существует заготовка Django-проекта без собственных моделей, форм, views и миграций приложений.

Документ служит источником архитектурных договорённостей для разработчика и ИИ-агента. Порядок внедрения определён в [ROADMAP.md](../ROADMAP.md), актуальные команды и состояние окружения — в [AGENTS.md](../AGENTS.md).

Если реализация сознательно отклоняется от документа, решение сначала фиксируется здесь или сразу после проверенного изменения. Документ не должен превращаться в историю всех обсуждений.

## 2. Контекст системы

«Ёлкин двор» — небольшой сезонный интернет-магазин живых новогодних деревьев и дополнительных товаров с доставкой по Ростову-на-Дону.

Основной сценарий:

1. Посетитель открывает главную страницу.
2. Выбирает категорию, товар, размер и количество.
3. Добавляет товары в корзину и при необходимости вводит промокод.
4. Заполняет контактные данные и адрес доставки.
5. Оформляет заказ без регистрации.
6. Видит подтверждение с номером, позициями и суммой.
7. Покупатель и магазин получают письма с данными заказа.
8. Менеджер обрабатывает заказ; оплата производится наличными при доставке.

### Основные требования

- Монолит Django и серверный рендеринг.
- Динамическое взаимодействие через HTMX.
- Tailwind CSS и daisyUI для стилей; Alpine.js только для локального UI.
- Небольшая стоимость эксплуатации и простое развёртывание.
- Нет онлайн-оплаты и публичной регистрации.
- Каталог, промокоды, пользователи и заказы управляются сотрудниками.
- Контакты покупателей доступны только авторизованным сотрудникам с правами.
- SEO важно для публичного каталога.
- SMTP не должен блокировать оформление заказа.

## 3. Архитектурные принципы

1. **Сервер является источником истины.** Цены, скидки, доступность вариантов и итог заказа не принимаются из браузера.
2. **Серверный рендеринг прежде всего.** Основной контент индексируется без JavaScript; HTMX улучшает взаимодействие.
3. **Минимально достаточная инфраструктура.** SQLite, сессии Django, Django Admin и очередь писем в БД вместо дополнительных сервисов.
4. **История заказа неизменна.** Изменение товара, цены или карточки покупателя не переписывает старые заказы.
5. **Короткие транзакции.** Внутри транзакции оформления нет SMTP и других медленных внешних вызовов.
6. **Тонкие views.** Проверки HTTP и форм остаются во views; прикладные операции выносятся в небольшие сервисные модули.
7. **Без преждевременных абстракций.** Repository, Unit of Work, собственный ORM-слой, отдельный API и микросервисы не вводятся.
8. **Безопасность по умолчанию.** CSRF, серверная валидация, ограничение staff-доступа и защита персональных данных обязательны.

## 4. Структура проекта и ответственность приложений

Целевая логическая структура:

```text
config/                 # настройки, корневые URL, WSGI/ASGI
shop/                   # каталог и публичные товарные страницы
cart/                   # сессионная корзина и её представления
orders/                 # покупатели, заказы, промокоды, оформление, письма
theme/                  # исходники и сборка Tailwind/daisyUI
templates/              # глобальные шаблоны и partials
static/                 # глобальная статика
docs/
    architecture.md     # этот документ
AGENTS.md               # актуальный контекст и команды для агента
ROADMAP.md              # этапы и критерии готовности
```

Отдельное приложение `pages` на начальном этапе не требуется. Главная может находиться в `shop`, поскольку преимущественно представляет каталог. Если позже появятся самостоятельные информационные страницы, их можно выделить без изменения заказов и корзины.

### `shop`

Отвечает за:

- категории;
- товары;
- размеры и варианты;
- цены вариантов;
- изображения;
- рекомендации между товарами;
- публичные запросы каталога;
- SEO-поля и индексируемые страницы.

`shop` не отвечает за корзину, оформление и покупателей.

### `cart`

Отвечает за:

- хранение состава корзины в сессии;
- добавление, удаление и изменение количества;
- построение актуального представления корзины;
- HTMX- и обычные HTTP-действия корзины;
- хранение введённого промокода как непроверенного пользовательского ввода до серверной проверки.

Отдельная таблица анонимных корзин в MVP не нужна. Восстановление корзины между разными устройствами не требуется.

### `orders`

Отвечает за:

- покупателей;
- заказы и их позиции;
- промокоды;
- единый расчёт скидки и итога;
- оформление заказа;
- подтверждение заказа;
- почтовую очередь и шаблоны уведомлений;
- рабочие операции менеджера, если они выходят за пределы стандартной админки.

Почта остаётся внутри `orders`, пока уведомления связаны только с заказами. Отдельное приложение `notifications` появляется только при реальном расширении каналов и сценариев.

### Пользователи

Отдельное приложение `users` не создаётся. Используются:

- стандартная модель `django.contrib.auth.User`;
- группы и permissions Django;
- Django Admin для управления пользователями;
- отсутствие публичной регистрации и самостоятельного сброса пароля.

## 5. Модель каталога

### `Category`

Основные данные:

- название;
- уникальный slug;
- описание;
- порядок отображения;
- активность;
- при необходимости SEO title и description.

Категории могут обозначать сосны, ели, пихты, подставки и украшения. «Дополнительные товары» — способ представления обычных категорий или товаров, а не отдельная модельная иерархия.

### `Product`

Основные данные:

- категория;
- название;
- уникальный slug;
- описание;
- активность;
- порядок;
- рекомендации;
- при необходимости SEO title и description.

Рекомендации реализуются несимметричной связью многие-ко-многим на `Product`. Если сосна рекомендует подставку, обратная рекомендация не появляется автоматически.

Нельзя допускать рекомендацию товара самим собой. Публичный интерфейс показывает только активные рекомендации.

### `Size` и `ProductVariant`

Предпочтительная сущность для покупки — `ProductVariant`, а не отдельный товар или размер.

Вариант содержит:

- товар;
- размер или его текстовое обозначение;
- цену;
- активность;
- при необходимости порядок.

Сочетание товара и размера уникально. Цена хранится в `DecimalField`; `float` для денег не используется.

Отдельная модель `Size` оправдана, если размеры действительно повторно используются и требуют самостоятельного управления. Если размер — только подпись конкретного варианта, допустимо хранить её в `ProductVariant`, чтобы не создавать ложный универсальный справочник.

**Решение (этап 1):** отдельная модель `Size` не создаётся; размер хранится текстовым полем `ProductVariant.size` (до 80 символов, нормализуется trim'ом). Уникальность `(product, size)` защищена constraint'ом `unique_size_per_product`.

### `ProductImage`

Содержит:

- товар;
- файл изображения;
- alt-текст;
- порядок;
- при необходимости признак основного изображения.

Основное изображение либо однозначно определяется порядком, либо защищается ограничением от нескольких главных изображений у одного товара.

## 6. Модель покупателей и заказов

### `Customer`

Предназначен для рабочей базы контактов и истории заказов.

Основные данные:

- имя;
- телефон в исходном или отображаемом виде;
- нормализованный телефон с индексом;
- email;
- даты создания и обновления;
- при необходимости служебная заметка менеджера.

Телефон и email не объявляются безусловно уникальными на уровне БД: контакт может быть общим, а неоднозначные совпадения нельзя автоматически объединять без риска смешать разных людей.

Первоначальная стратегия связывания:

1. Нормализовать телефон.
2. Найти точных кандидатов по нормализованному телефону.
3. Связать заказ с существующей записью только при однозначном совпадении по согласованному правилу.
4. При неоднозначности создать отдельную запись; ручное объединение дубликатов может быть добавлено позже.

Дубликаты предпочтительнее автоматического объединения разных покупателей. Все операции объединения в будущем должны сохранять связи заказов.

### `Order`

Содержит два вида данных:

**Связи и служебные поля:**

- внутренний ID;
- публичный отображаемый номер;
- связь с `Customer`;
- статус;
- даты создания и обновления.

**Снимок оформления:**

- имя покупателя;
- телефон;
- email;
- адрес доставки;
- примечание;
- подытог;
- скидка;
- итог;
- код и основные параметры применённого промокода.

Снимок контактов необходим даже при наличии `Customer`: карточка покупателя может измениться, а данные конкретной доставки должны остаться прежними.

Связь `Order.customer` допускает `NULL` и использует поведение, сохраняющее заказ при удалении карточки покупателя. Исторический заказ не должен каскадно удаляться вместе с покупателем.

### Номер заказа

Внутренним ключом остаётся обычный целочисленный ID. Отображаемый номер формируется детерминированно после получения ID, например `ЁД-2026-000125`, и сохраняется уникальным полем.

Не требуется отдельный генератор последовательностей или распределённый сервис номеров. Публичный номер не должен сам по себе давать доступ к деталям заказа.

### `OrderItem`

Содержит:

- заказ;
- необязательные служебные ссылки на товар и вариант;
- снимок названия товара;
- снимок размера;
- цену за единицу на момент заказа;
- количество;
- сумму позиции.

Ссылки на каталог не заменяют снимки. При удалении товара или варианта позиция заказа сохраняется. При изменении цены товара старая позиция не пересчитывается.

### Статусы заказа

Минимальный набор:

- `new` — новый;
- `confirmed` — подтверждён;
- `delivering` — в доставке;
- `completed` — выполнен;
- `cancelled` — отменён.

Статус оплаты в MVP не нужен, поскольку существует только оплата наличными при доставке. Если бухгалтерскому процессу позже потребуется факт оплаты, его добавляют отдельно, не смешивая со статусом доставки.

## 7. Промокоды и расчёт денег

### `PromoCode`

Минимальные данные:

- нормализованный уникальный код;
- активность;
- тип скидки: процентная или фиксированная;
- величина;
- начало и окончание действия;
- минимальная сумма, если требуется.

Персональные промокоды, лимиты на пользователя, сложные комбинации акций и автоматическое начисление бонусов не входят в MVP.

### Единый расчёт

Расчёт подытога, скидки и итога находится в одном модуле `orders`, поскольку `orders` владеет промокодами и правилами оформления. Этот модуль:

- не зависит от `request` и сессии;
- принимает актуальные варианты, количества и проверяемый промокод;
- возвращает подытог, скидку и итог;
- используется и для отображения корзины, и при оформлении;
- выполняет согласованное округление;
- не допускает итог меньше нуля.

В корзине нельзя хранить рассчитанную скидку как доверенное значение. Сохраняется только код, а результат каждый раз пересчитывается.

## 8. Корзина

### Формат хранения

В сессии сохраняются только:

- ID варианта;
- количество;
- введённый промокод, если он есть.

Не сохраняются как источник истины:

- цена;
- название;
- скидка;
- итоговая сумма.

### Поведение

При каждом построении корзины система заново получает варианты из БД и рассчитывает суммы. Неактивные или исчезнувшие позиции не могут быть оформлены; пользователю показывается понятное сообщение.

Операции корзины инкапсулируются в `cart/services.py` или аналогичном небольшом модуле. Views отвечают за HTTP, формы, редиректы и выбор полного шаблона либо HTMX-partial, но не содержат размноженную логику изменения сессии.

## 9. Оформление заказа

### Последовательность

1. Проверить, что корзина не пуста.
2. Провалидировать форму контактов и адреса.
3. Повторно загрузить варианты и проверить их активность.
4. Повторно рассчитать цены и промокод.
5. Нормализовать контактные данные.
6. Найти или создать покупателя по согласованной стратегии.
7. В короткой транзакции создать заказ, позиции и записи исходящих писем.
8. Сформировать публичный номер заказа.
9. После успешного commit очистить корзину.
10. Перенаправить на подтверждение, чтобы повторный refresh не повторял POST.

### Транзакционная граница

В одну транзакцию входят:

- `Customer`, если создаётся новая запись;
- `Order`;
- все `OrderItem`;
- две записи почтовой очереди — покупателю и магазину.

SMTP-отправка, рендеринг тяжёлых внешних ресурсов и другие сетевые операции в транзакцию не входят.

### Подтверждение

Страница содержит:

- номер заказа;
- список всех позиций;
- размеры и количество;
- подытог, скидку и итог;
- адрес и контакты, если это предусмотрено дизайном.

Доступ к подтверждению анонимного заказа выдаётся через текущую сессию после оформления или через отдельный подписанный механизм. Простой URL с перебираемым ID не должен раскрывать произвольные заказы и персональные данные.

### Повторные запросы

Двойной click, refresh и повторная отправка не должны без контроля создавать несколько заказов. Для MVP достаточно сочетания:

- POST/Redirect/GET;
- очистки корзины после commit;
- отключения кнопки в UI как вспомогательной меры;
- при необходимости одноразового checkout-token в сессии.

UI-блокировка кнопки сама по себе защитой не считается.

## 10. Почтовая очередь без Redis

### Решение

Использовать таблицу исходящих писем и management-команду, запускаемую планировщиком ОС. На Linux это cron, на Windows — Планировщик заданий.

Отдельный `threading.Thread` внутри web-запроса не является основным механизмом: при перезапуске worker письмо может потеряться, а контроль повторов и ошибок усложняется.

### `OutgoingEmail`

Минимальные данные:

- заказ;
- получатель;
- тема;
- текстовое тело;
- при необходимости HTML-тело;
- статус: `pending`, `sending`, `sent`, `failed`;
- число попыток;
- время следующей попытки;
- дата отправки;
- последняя ошибка;
- технический ключ для предотвращения повторной постановки одинакового письма.

Письмо создаётся вместе с заказом. Если транзакция заказа откатывается, запись письма также исчезает.

### Обработчик

Management-команда `send_order_emails`:

1. Выбирает ограниченную партию писем, готовых к отправке.
2. Отмечает обрабатываемые записи.
3. Выполняет SMTP-вызовы вне транзакции создания заказа и без удержания длинной блокировки БД.
4. Отмечает успех или планирует повторную попытку.
5. После исчерпания попыток переводит письмо в `failed`.
6. Пишет диагностический лог без секретов.

В простом deployment запускается один обработчик. Если планировщик может запускать пересекающиеся процессы, требуется защита от одновременной обработки одной записи.

Семантика отправки — минимум одна попытка с возможными повторами. Редкий сбой после фактической отправки, но до записи статуса может привести к повторному письму; это предпочтительнее потери уведомления.

### Конфигурация

Локально используется console backend. Реальные SMTP-параметры поступают из `.env` через действующий для проекта интерфейс `MAILERS`. Пароли не попадают в Git, шаблоны писем или логи.

## 11. Views, шаблоны, HTMX и Alpine.js

### Views

Views отвечают за:

- получение и проверку HTTP-входных данных;
- вызов прикладных операций;
- выбор шаблона;
- редиректы и HTTP-статусы;
- возврат полного шаблона или partial для HTMX.

Сложные прикладные операции не размножаются по нескольким views.

### Шаблоны

`templates/base.html` содержит только общий каркас. Главная страница — отдельный шаблон. Повторяющиеся блоки выносятся в includes, а ответы HTMX — в небольшие partials.

Наличие partial не означает отдельный параллельный API: используются те же серверные правила и HTML-шаблоны.

### HTMX

Подходит для:

- выбора размера и обновления цены;
- действий корзины;
- счётчика корзины;
- промокода;
- отправки checkout-формы с серверной валидацией.

Все изменяющие HTMX-запросы проходят CSRF-проверку. Ошибки формы возвращаются с корректным статусом и отображаются рядом с полями.

### Alpine.js

Используется для локального состояния интерфейса:

- мобильное меню;
- модальные окна;
- переключатели галереи;
- вспомогательные UI-действия.

Alpine не должен становиться вторым независимым источником состояния корзины или цены.

## 12. URL и SEO

Даже при одностраничной главной нужны серверные публичные URL:

- главная;
- страница категории;
- страница товара;
- корзина;
- оформление;
- подтверждение заказа.

Главная содержит секции баннера, каталога по категориям, дополнительных товаров, контактов и подвала.

SEO-основа:

- уникальные и человекочитаемые slug;
- корректные title и meta description;
- canonical;
- семантическая иерархия заголовков;
- alt изображений;
- `sitemap.xml`;
- `robots.txt`;
- серверный рендеринг основного контента;
- быстрые оптимизированные изображения с заданными размерами.

Корзина, оформление, подтверждение и staff-разделы не должны индексироваться. Структурированные данные Product/Offer добавляются только при наличии корректных публичных данных о товаре и цене.

## 13. Авторизация и права

Покупателю авторизация не нужна.

Для сотрудников используются стандартные пользователи Django. Предлагаемые группы:

- **Менеджер:** просмотр заказов и покупателей, изменение разрешённых статусов.
- **Администратор:** управление каталогом, промокодами, пользователями и остальными настройками.

Django Admin является staff-интерфейсом MVP. Собственный кабинет оправдан только отдельным требованием к интерфейсу или процессу.

Проверки прав выполняются на сервере. Скрытие пунктов меню не считается контролем доступа.

## 14. Безопасность и персональные данные

Обязательные меры:

- CSRF для всех изменяющих POST/HTMX-запросов;
- серверная валидация и ограничение длины полей;
- серверный пересчёт денег;
- отсутствие публичного просмотра заказа по последовательному ID;
- ограничение доступа к контактам и заказам;
- `DEBUG=False` в production;
- корректные `ALLOWED_HOSTS`, HTTPS и secure-cookie;
- секреты только в окружении;
- отсутствие паролей, SMTP-учётных данных и лишних персональных данных в логах;
- простая защита публичной формы от спама, например honeypot и ограничение слишком частых отправок;
- резервное копирование БД и медиа.

Письма содержат необходимые данные заказа, но не должны включать служебные секреты или ссылки, открывающие произвольный доступ к заказу.

## 15. Хранение и эксплуатация

### SQLite

SQLite достаточен для небольшого сезонного магазина при условии:

- коротких транзакций;
- отсутствия SMTP внутри транзакций;
- одного простого обработчика почтовой очереди;
- регулярного резервного копирования;
- контроля дискового пространства.

Переход на PostgreSQL рассматривается при росте одновременных записей, появлении нескольких обработчиков или новых требований к эксплуатации, а не заранее.

### Медиа

Изображения товаров хранятся в media-хранилище. В production каталог медиа должен быть постоянным и входить в резервные копии. Переустановка приложения не должна удалять загруженные изображения.

### Резервные копии

Резервное копирование должно включать:

- `db.sqlite3`;
- загруженные медиа;
- при необходимости экспорт критичных настроек без секретов.

Наличие задания backup недостаточно: восстановление проверяется на отдельной копии.

## 16. Тестовая стратегия

### Модульные тесты

- операции корзины;
- нормализация контактов;
- расчёт подытога, скидки и итога;
- сроки и активность промокода;
- округление денежных значений;
- формирование номера заказа;
- правила поиска покупателя.

### Интеграционные тесты

- публичный каталог показывает только активные записи;
- добавление и изменение корзины;
- обычные POST и HTMX-запросы;
- успешное оформление;
- пустая корзина и невалидная форма;
- изменение каталога не меняет старый заказ;
- создание заказа и двух писем атомарно;
- очистка корзины только после успеха;
- права менеджера и анонима;
- отправка и повторные попытки почты с тестовым backend.

### Ручные проверки

- мобильный и полноэкранный дизайн;
- галерея, меню и модальные окна;
- клавиатурная доступность;
- повторный click и refresh после заказа;
- медленный SMTP;
- восстановление резервной копии;
- полный путь заказа до обработки менеджером.

## 17. Границы расширения

Архитектура допускает последующее добавление:

- собственных staff-страниц поверх существующих прав;
- PostgreSQL без изменения предметной модели;
- внешнего worker для обработки той же очереди;
- дополнительных каналов уведомлений;
- складских остатков;
- ручного объединения покупателей;
- более сложных промокодов.

Эти возможности не реализуются заранее. Отдельные триггеры для пересмотра архитектуры:

- SMTP-провайдер требует сложной интеграции с высокой частотой событий;
- появляются несколько одновременно работающих обработчиков очереди;
- SQLite становится источником блокировок при реальной нагрузке;
- менеджерам объективно недостаточно Django Admin;
- появляются несколько городов, складов или способов оплаты;
- возникает необходимость в личном кабинете покупателя.
